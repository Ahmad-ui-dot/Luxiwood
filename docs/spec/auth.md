# Авторизация

Код: `apps/api/src/auth/`. Эндпоинты — раздел «Авторизация» в [api.md](./api.md).

## 1. Роли

| Роль | Как получить | Что может |
|---|---|---|
| Гость | — | каталог, расчёт цены, «Встанет ли у вас?», конструктор, оформление и отслеживание заказа |
| Покупатель (`CLIENT`) | `POST /api/auth/register` | всё, что гость, + «Мой кабинет» (заказы, отмена на этапе NEW, избранное), отзывы |
| Администратор (`ADMIN`) | создаётся seed из `ADMIN_EMAIL` / `ADMIN_PASSWORD` | всё в `/api/admin/*`, а также всё, что доступно любому вошедшему |

Регистрации администраторов через сайт нет. Отзывы оставляет только `CLIENT` (`@Roles('CLIENT')`).

## 2. Регистрация

`POST /api/auth/register` `{ name, email, phone?, password }` → `{ accessToken, user }` — покупатель сразу вошёл.

| Поле | Правило |
|---|---|
| `name` | 2–50 символов, хотя бы одна буква, без `@`. Это логин, уникален **без учёта регистра** («Мадина» и «мадина» — одно имя) |
| `email` | обязателен, уникален, хранится в нижнем регистре |
| `phone` | необязателен: +992 и 9 цифр, пробелы допускаются; хранится без пробелов (`+992930000005`). Только для связи по заказам, для входа не используется |
| `password` | 6–100 символов |

Занятое имя → 409 «Имя «Мадина» уже занято — выберите другое, например «Мадина К.»». Занятые телефон или email → 409 со своим текстом.

## 3. Вход

`POST /api/auth/login` `{ login, password }` → `{ accessToken, user }`.

- Если в `login` есть `@` — ищем по email, иначе по имени без учёта регистра.
- Неверный логин или пароль → 401 «Неверный логин или пароль» (одинаково для обоих случаев).
- Пароли хранятся только как bcrypt-хеш (10 раундов).

## 4. Токен

- JWT подписывается `JWT_SECRET`, живёт **7 дней**. Без `JWT_SECRET` API не запускается.
- Содержимое: `{ sub: userId, role, iat }`.
- Передаётся в заголовке `Authorization: Bearer <токен>`. Cookies и refresh-токенов нет — по истечении срока нужно войти заново.
- На сайте (план) токен хранится в `localStorage` и подставляется в каждый запрос; на 401 сайт удаляет токен и отправляет на страницу входа.

## 5. Как проверяется доступ

`AuthGuard` (`auth.guard.ts`) на каждом закрытом запросе:

1. Берёт токен из заголовка. Нет токена → 401 «Нужно войти: передайте токен…» (для `@OptionalAuth()` — запрос идёт дальше как гостевой).
2. Проверяет подпись и срок. Не прошёл → 401 «Токен недействителен или устарел — войдите заново».
3. Находит пользователя в базе. **Роль берётся из базы, а не из токена.** Пользователя нет → 401.
4. Если токен выдан раньше `passwordChangedAt` → 401 «Пароль был изменён — войдите заново».
5. Кладёт `{ id, role }` в `request.user`, достаётся в контроллере через `@CurrentUser()`.
6. Роль не подходит под `@Roles(...)` → 403 «Недостаточно прав для этого действия».

| Декоратор | Значение |
|---|---|
| `@Auth()` | нужен вход, любая роль |
| `@Roles('ADMIN')` | нужна одна из ролей (включает `@Auth()`) |
| `@OptionalAuth()` | вход не обязателен; если токен передан — он проверяется и пользователь известен |
| `@CurrentUser()` | текущий пользователь `{ id, role }` в параметрах метода |

Декораторы сразу добавляют в Swagger замочек и ответы 401/403.

## 6. Профиль

- `GET /api/auth/me` — свой профиль без пароля.
- `PATCH /api/auth/me` `{ name?, phone?, defaultAddress? }` — меняются только переданные поля; имя и телефон проверяются на занятость (кроме себя). Email не меняется.

## 7. Смена пароля

`PATCH /api/auth/password` `{ currentPassword, newPassword }` → `{ accessToken, user }`.

- Неверный текущий пароль → 400; новый совпадает с текущим → 400.
- Записывается `passwordChangedAt = now`, поэтому **все прежние токены перестают действовать**. В ответе новый токен — сайт должен сразу заменить им старый.

## 8. Восстановление пароля

```
1. POST /api/auth/forgot-password { email }
   → всегда 200 «Если этот email зарегистрирован, мы отправили на него код…»
   Если пользователь есть: старые коды удаляются, создаётся новый 6-значный код,
   в базе хранится только его bcrypt-хеш, срок — 15 минут. Код уходит письмом.
2. POST /api/auth/reset-password { email, code, newPassword }
   → { accessToken, user } — сразу вход, прежние токены перестают действовать
```

| Правило | Значение |
|---|---|
| Срок кода | 15 минут |
| Попыток ввода | 5; после 5-й неверной код больше не принимается, нужен новый |
| Код одноразовый | после успешного сброса все коды пользователя удаляются |
| Любая ошибка кода | 400 «Код неверный или устарел. Запросите новый код» — без подсказки, что именно не так |
| Лимиты | запрос кода — 5 в минуту, ввод кода — 10 в минуту с одного IP |

**Почта:** `MailService` отправляет через Gmail (`SMTP_USER` + пароль приложения в `SMTP_PASS`). Если они пустые: при разработке письмо печатается в консоль API, в production — 503 «Не удалось отправить письмо. Попробуйте позже».

## 9. Лимиты запросов

| Путь | Лимит с одного IP |
|---|---|
| `POST /auth/register`, `POST /auth/login`, `POST /auth/reset-password` | 10 в минуту |
| `POST /auth/forgot-password` | 5 в минуту |

Превышение → 429 «Слишком много запросов. Попробуйте через минуту».
